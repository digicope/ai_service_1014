# AI 서비스 기획자를 위한 파이썬 언어와 활용법

> 대상: 프로그래밍 비전공자인 AI 서비스 기획자  
> 목적: 파이썬을 처음부터 직접 작성하기보다, 업무 요구사항을 코드로 바꾸고 실행 결과를 검토하는 데 필요한 언어 감각을 익힌다.  
> 실습 환경: Google Colab Enterprise, Gemini, Antigravity  
> 함께 보는 자료: `AI 주도형 파이썬 스크립트 실무 실습 프롬프트.txt`, `AI 주도형 파이썬 스크립트 실무 코드 작성 실습.ipynb`

---

## 1. 이 문서에서 얻는 것

이 문서를 읽고 나면 다음을 할 수 있다.

- 파이썬 코드의 큰 구조를 읽고, 각 줄이 서비스 업무의 어느 단계인지 말할 수 있다.
- 매출, 만족도, 이탈 위험처럼 기획 지표를 계산하는 요구사항을 AI에게 정확히 전달할 수 있다.
- 실행 결과와 AI의 해석을 구분하고, 가상 데이터로 만든 숫자를 실제 서비스 성과처럼 쓰지 않을 수 있다.
- Pandas, 시각화, 기초 예측, Gemini API가 기획 업무의 어느 지점에 놓이는지 설명할 수 있다.

개발자가 되는 과정이 아니다. **요구사항을 실행 가능한 형태로 적고, 나온 결과를 기획 판단의 근거로 쓰는 과정**이다.

---

## 2. 기획자에게 파이썬이 필요한 이유

AI 서비스 기획에서 자주 막히는 지점은 “아이디어가 없어서”보다 “숫자가 없어서”인 경우가 많다.

| 기획 질문 | 파이썬이 해주는 일 |
| --- | --- |
| 어떤 상품이 매출의 대부분을 차지하는가 | 수량 × 단가, 비중, 최댓값 계산 |
| 만족도 4점 미만 과정은 어디인가 | 조건에 맞는 행만 골라 표로 출력 |
| 연령대별 구매 금액이 다른가 | 그룹별 평균 비교 |
| 가입은 느는데 유료 전환은 낮은가 | 월별 추이를 그래프로 비교 |
| 누가 중도 이탈할 가능성이 높은가 | 학습 데이터로 분류 모델을 만들고 성능 지표를 확인 |
| 분석 숫자를 운영 보고서로 바꾸려면 | 계산 결과를 Gemini에 넘겨 문장으로 정리 |

기획자가 코드를 한 줄씩 외울 필요는 없다. 다만 아래 네 가지는 직접 판단해야 한다.

1. **입력**: 어떤 데이터 항목이 필요한가
2. **규칙**: 무엇을 계산하고, 어떤 값을 오류로 볼 것인가
3. **출력**: 표, 그래프, 점수, 문장 중 무엇이 결정에 쓰이는가
4. **한계**: 이 숫자가 가상 데이터인지, 인과가 아니라 상관인지, 개인정보가 포함되는지

## 3. 파이썬이란

파이썬은 데이터를 읽고, 계산하고, 결과를 보여주는 데 많이 쓰는 프로그래밍 언어다. AI 서비스 실무에서는 보통 다음 역할을 한다.

- **스크립트**: 한 번 실행하면 매출 집계, 정제, 그래프 저장처럼 정해진 작업을 끝낸다.
- **노트북**: Colab처럼 코드와 설명, 실행 결과를 한 화면에 쌓는다. 기획 실습과 분석 공유에 맞다.
- **서비스의 한 조각**: 예측 API, 리포트 생성, 데이터 점검 배치처럼 제품 기능의 뒤편에서 동작한다.

이 과정의 실습은 **노트북(Colab) 안의 스크립트**다. 웹 서비스 전체를 만드는 범위와, Colab에서 바로 확인하는 범위를 항상 구분한다.

### 3.1 기획자가 알아 두면 좋은 언어의 특징

- 문장 끝의 세미콜론 없이, **들여쓰기**로 묶음의 범위를 표시한다. 스페이스 개수가 어긋나면 실행이 멈춘다.
- 위에서 아래로 한 줄씩 실행한다. 노트북에서는 **셀 단위**로 실행하므로, 위 셀을 실행하지 않으면 아래 셀이 실패할 수 있다.
- 결과를 화면이 아니라 `print`나 표 출력으로 확인한다. “코드가 맞다”와 “화면에 숫자가 나왔다”는 같은 뜻으로 본다.
- 표준 기능만으로 부족한 일은 **라이브러리**를 불러와 처리한다. 표는 Pandas, 그래프는 Matplotlib, 예측은 Scikit-learn이 대표적이다.

### 3.2 이 과정에서 파이썬을 쓰는 방식

```text
업무를 말로 적는다
    → Gemini 또는 Antigravity가 파이썬 코드를 만든다
    → Colab에서 실행한다
    → 표·그래프·오류 메시지를 읽는다
    → 요구사항과 다른 부분을 다시 지시한다
    → 기획 인사이트와 추가 검증 항목을 정리한다
```

Antigravity는 서비스 요구사항을 코드로 바꾸는 작업 환경으로 쓰고, Colab Enterprise는 그 코드를 실행해 숫자를 확인하는 환경으로 쓴다. Gemini는 코드 생성, 오류 설명, 분석 문장화에 쓴다.

## 4. 코드를 읽는 최소 문법

아래 예시는 외우기 위한 문법이 아니다. AI가 만든 코드에서 **어디가 데이터이고, 어디가 규칙이고, 어디가 출력인지** 찾기 위한 표지판이다.

### 4.1 변수: 이름을 붙인 값

```python
상품명 = "무선 이어폰"
판매수량 = 120
단가 = 39000
매출액 = 판매수량 * 단가
```

변수는 상자에 이름을 붙이는 일과 같다. `매출액`이라는 이름 안에 계산 결과가 들어간다. 기획서의 지표 이름과 코드의 변수 이름을 같게 두면, 나중에 코드를 다시 읽기 쉽다.

확인 포인트

- 단위가 분명한가. 금액인지, 비율인지, 점수인지.
- 비율이 0.18인지 18인지. 둘 다 “18%”로 말할 수 있어 보고서에서 자주 틀린다.
- 한글 변수명은 실습에서 읽기 좋다. 팀 코드에서는 영어 이름이 더 흔한 편이다. 어느 쪽이든 **의미가 드러나는 이름**이면 된다.

### 4.2 자료형: 값의 종류

| 자료형 | 예시 | 기획에서의 예 |
| --- | --- | --- |
| 정수 `int` | `120` | 판매 수량, 가입자 수 |
| 실수 `float` | `4.2`, `0.18` | 평균 만족도, 전환율 |
| 문자열 `str` | `"2026-03-01"` | 상품명, 고객 ID, 날짜 문자 |
| 불리언 `bool` | `True`, `False` | 이탈 여부, 검증 통과 여부 |
| 리스트 `list` | `["A과정", "B과정"]` | 같은 종류의 값을 순서대로 묶음 |
| 딕셔너리 `dict` | `{"수료율": 0.72}` | 지표 이름과 값을 짝으로 보관 |
| 결측 `None` | 비어 있음 | 미입력 연령, 미응답 만족도 |

문자열로 저장된 숫자 `"4.5"`는 평균 계산에 바로 쓸 수 없다. 날짜도 `"2026/3/1"`, `"2026-03-01"`, `"3월 1일"`이 섞이면 기간 필터가 깨진다. 데이터 품질 실습에서 이 차이를 직접 다룬다.

### 4.3 리스트와 딕셔너리

```python
과정목록 = ["파이썬 입문", "데이터 분석", "서비스 기획"]
점수 = {"파이썬 입문": 4.6, "데이터 분석": 3.7}
```

- 리스트는 **순서 있는 묶음**이다. 첫 항목은 0번이다. `과정목록[0]`은 `"파이썬 입문"`이다.
- 딕셔너리는 **이름표가 붙은 묶음**이다. `점수["데이터 분석"]`은 `3.7`이다.
- Gemini에 분석 결과를 넘길 때는 딕셔너리나 JSON이 잘 맞는다. 지표 이름이 키로 고정되기 때문이다.

### 4.4 조건: 기준을 코드로 적기

```python
if 평균만족도 < 4:
    print("개선 검토 대상")
else:
    print("기준 충족")
```

기획서의 “4점 미만이면 개선 대상으로 표시”가 곧 조건문이다. 기준값을 코드 중간에 숨기지 말고, 문서와 코드에 같은 숫자로 적는다.

기준을 정할 때 같이 적을 항목

- 경계 포함 여부: 4점 미만인가, 4점 이하인가
- 결측이면 대상에서 빼는가, 검토 대기인가
- 소수 점수가 있을 때 반올림 자릿수

### 4.5 반복: 같은 계산을 여러 대상에 적용

```python
for 상품 in 상품목록:
    매출액 = 상품["수량"] * 상품["단가"]
    print(상품["상품명"], 매출액)
```

상품 5개든 고객 10만 명이든, 반복문은 “각 행에 같은 규칙을 적용하라”는 뜻이다. 기획자는 반복 대상(상품, 과정, 고객, 월)과 한 번에 계산할 지표를 요구사항에 적으면 된다.

### 4.6 함수: 이름을 붙인 작업 묶음

```python
def 매출액계산(수량, 단가):
    return 수량 * 단가
```

함수는 입력(`수량`, `단가`)을 받아 출력(`return`)을 돌려준다. 서비스 기능 정의와 구조가 같다.

```text
기능명: 매출액 계산
입력: 판매 수량, 단가
처리: 수량 × 단가
출력: 매출액
예외: 수량이나 단가가 음수이면 계산하지 않고 검토 대상으로 표시
```

이 네 줄을 요구사항으로 적으면, AI가 함수나 분석 단계로 옮기기 쉽다.

### 4.7 주석: 코드가 아니라 사람용 설명

```python
# 만족도 4점 미만 과정만 개선 검토 대상으로 분리한다
검토대상 = 만족도표[만족도표["평균만족도"] < 4]
```

`#` 뒤는 실행되지 않는다. 실습 코드에서는 한글 주석으로 “이 줄이 기획 규칙의 어디인지”를 남긴다. 주석과 실제 계산이 다르면 주석이 아니라 **실행 결과**를 믿는다.

### 4.8 라이브러리 불러오기

```python
import pandas as pd
```

`import`는 이미 만들어 둔 도구 상자를 연다는 뜻이다. `as pd`는 그 도구를 `pd`라는 짧은 이름으로 쓰겠다는 약속이다.

이 과정의 실습에서 자주 보는 이름

| 코드에 보이는 이름 | 하는 일 | 실습 |
| --- | --- | --- |
| 기본 파이썬만 사용 | 작은 표의 합계, 비중, 최댓값 | 실습 1 |
| `pandas` (`pd`) | 표 생성, 필터, 그룹 평균, 결측 처리 | 실습 2~6, 8 |
| `numpy` (`np`) | 수치 배열, 난수 데이터 생성 | 실습 3, 7 |
| `matplotlib`, `seaborn` | 선 그래프, 막대그래프, 분포 | 실습 5, 6 |
| `sklearn` | 학습/테스트 분리, 분류, 성능 지표 | 실습 7 |
| Google Gen AI SDK | 분석 결과를 Gemini에 전달 | 실습 8 |

요구사항에 “외부 패키지를 설치하지 말 것”이 있으면, Colab에 기본 포함된 라이브러리만 쓰고 `pip install`을 넣지 않는다.

## 5. 실행이 안 될 때 읽는 법

오류 메시지의 **마지막 몇 줄**에 원인이 있다. 기획자가 메시지를 고칠 필요는 없고, 유형을 구분해 AI에게 다시 시키면 된다.

| 자주 보는 오류 | 의미 | 기획자가 확인할 것 |
| --- | --- | --- |
| `SyntaxError` | 문법 오타, 들여쓰기, 따옴표 미닫힘 | 코드를 수정하기보다 오류 전문을 붙여 재생성 |
| `NameError` | 아직 없는 이름을 사용 | 위 셀을 실행했는지, 변수명 오타인지 |
| `KeyError` | 표나 딕셔너리에 없는 열 이름 | 요구한 컬럼명과 코드의 컬럼명이 같은지 |
| `TypeError` | 문자열과 숫자를 그대로 더하는 등 종류가 어긋남 | 연령, 금액, 날짜의 형식 |
| `ValueError` | 값은 있으나 규칙에 안 맞음 | 만족도 범위, 날짜 형식, 빈 문자열 |
| 모듈 없음 | 라이브러리를 찾지 못함 | Colab에서 실행 중인지, 설치가 허용된 실습인지 |

AI에게 오류를 넘길 때는 이렇게 적는다.

```text
아래 코드를 Colab에서 실행했더니 오류가 났다.
1) 오류 메시지를 그대로 붙인다.
2) 기대한 결과를 한 줄로 적는다.
3) 원인, 수정 방법, 수정된 코드 순서로 다시 작성해 달라.
```

오류를 숨기거나, 실행하지 않은 채 예상 숫자를 문장으로 만들지 않는다.

## 6. 표로 일하는 법: Pandas

서비스 데이터는 대부분 표다. 행은 고객·주문·수강 기록이고, 열은 그 기록의 항목이다. Pandas의 `DataFrame`이 이 표를 코드에서 다루는 기본 도구다.

```python
import pandas as pd

표 = pd.DataFrame({
    "과정명": ["A", "B"],
    "신청자": [100, 80],
    "수료자": [70, 40],
})
표["수료율"] = 표["수료자"] / 표["신청자"]
```

기획자가 표 설계 때 정하는 것

- **한 행의 단위**: 고객 1명인가, 주문 1건인가, 과정-월 1개인가. 단위가 섞이면 평균이 왜곡된다.
- **열의 정의**: 수료율은 수료자 ÷ 신청자인가, 수료자 ÷ 결제자인가.
- **식별자**: 고객 ID가 사람을 구분하는 키인지. 같은 ID의 구매 기록이 여러 행일 수 있다. 중복 ID를 무조건 삭제하면 구매 이력까지 사라진다.
- **기간**: 가입일, 운영 월의 형식을 하나로 고정한다.

자주 쓰는 작업과 기획 표현

| 기획 표현 | 코드에서 일어나는 일 |
| --- | --- |
| 상위 5건만 보자 | `head(5)` |
| 구매 금액 평균, 중앙값, 최댓값 | `mean()`, `median()`, `max()` |
| 상위 20% 고객 | 금액 기준 분위수로 행을 필터 |
| 연령대별 평균 구매 금액 | 연령대를 나눈 뒤 그룹별 평균 |
| 4점 미만만 | 조건 필터 |
| 월별 합계 | 월로 묶은 뒤 합계 |

평균만 보면 소수의 고액 구매자가 전체를 끌어올린다. 중앙값, 분포, 상위 비중을 같이 본다.

---

## 7. 데이터 품질: 계산 전에 정하는 규칙

잘못된 데이터로 계산하면 코드는 정상 종료되고, 의사결정만 틀린다. 클렌징은 “지저분한 칸을 지우는 일”이 아니라 **삭제, 보정, 검토 대기를 기준표로 나누는 일**이다.

| 문제 | 예시 | 실무에서 바로 정할 기준 |
| --- | --- | --- |
| 결측 | 연령이 비어 있음 | 분석에서 제외할지, 별도 집단으로 둘지 |
| 중복 | 같은 고객 ID가 두 행 | 사람 중복인지, 구매 이력 여러 건인지 |
| 범위 이탈 | 만족도 7점, 연령 -3 | 입력 오류로 보고 검토 대기 |
| 부호 오류 | 구매 금액이 음수 | 환불인지 입력 오류인지 구분 |
| 형식 불일치 | 날짜 표기가 제각각 | 한 형식으로 바꾼 뒤 실패 건은 검토 |

이 과정에서 지키는 원칙

- 원본 표는 남겨 두고, 정제 결과는 다른 표에 저장한다.
- 처리 기준을 주석과 결과 요약에 같이 남긴다.
- 정제 전후 행 수와 결측 수를 비교한다.
- 실제 서비스에서는 삭제와 보정에 담당자 승인이 필요한 항목을 따로 적는다.

---

## 8. 시각화: 그래프는 주장의 근거 화면

그래프는 장식이 아니라, 표에서 놓치기 쉬운 비교를 한 화면에 올리는 장치다.

| 보고 싶은 것 | 맞는 그래프 | 기획 질문 예 |
| --- | --- | --- |
| 시간에 따른 변화 | 선 그래프 | 월별 가입자는 늘고 있는가 |
| 항목 간 크기 비교 | 막대그래프 | 과정별 수료율 차이는 얼마인가 |
| 값이 어디에 몰리는지 | 분포 그래프 | 만족도가 4~5에 몰리는가, 1~2에도 뭉쳐 있는가 |

읽을 때 같이 보는 것

- 축 이름과 단위가 있는가
- 제목이 질문형 또는 결론형으로 적혀 있는가
- 가상 데이터라는 표시가 있는가
- 가입자 수와 전환율이 한 축에 섞여 눈속임이 생기지 않는가

그래프가 보여주는 것은 패턴이다. 원인(“가격 때문이다”, “콘텐츠가 어렵다”)은 추가 데이터로 확인하기 전까지 **가설**로 적는다.

---

## 9. 기초 예측: 기획자가 모델에서 볼 항목

Scikit-learn으로 만드는 기초 분류 모델은 “AI가 답을 아는 기능”이 아니다. **과거 데이터의 패턴으로 미래 또는 미확인 건의 가능성을 점수로 내는 기능**이다.

이탈 예측 예시를 서비스 언어로 옮기면 다음과 같다.

| 모델 용어 | 기획 언어 |
| --- | --- |
| 특성(feature) | 주간 학습 시간, 접속 횟수, 과제 제출률, 진도율 |
| 정답(label) | 중도 이탈 여부 |
| 학습 데이터 | 규칙을 맞출 때 쓰는 과거 건 |
| 테스트 데이터 | 맞춰 본 뒤 성적을 내는 별도 건 |
| 예측값 | 이 수강생을 이탈 위험으로 볼지 |

학습에 쓴 데이터로 성적을 내면 점수가 실제보다 좋아 보인다. 그래서 학습과 테스트를 나눈다. 정답이나 미래 정보가 입력에 섞이면 **데이터 누수**가 되고, 서비스에 나갔을 때 성능이 떨어진다.

### 9.1 성능 지표를 서비스 말로 바꾸기

이탈을 “위험”으로 예측하는 상황이라고 두면 다음과 같다.

| 지표 | 한 줄 의미 | 기획에서 아픈 지점 |
| --- | --- | --- |
| 정확도 | 전체 중 맞춘 비율 | 이탈이 드물면, 전부 “유지”로 찍어도 정확도가 높다 |
| 정밀도 | 위험이라고 한 사람 중 실제 이탈 비율 | 낮으면 정상 수강생을 위험군으로 많이 부른다 |
| 재현율 | 실제 이탈자 중 위험이라고 찾아낸 비율 | 낮으면 이탈할 사람을 놓친다 |
| F1 | 정밀도와 재현율의 균형 | 둘 중 하나만 좋을 때 착시를 줄인다 |

혼동 행렬은 네 칸이다. 맞춘 유지, 맞춘 이탈, 놓친 이탈, 잘못 부른 위험군. 서비스 정책은 이 칸의 비용으로 정한다.

- 놓친 이탈의 비용이 크면 재현율을 우선하고, 개입은 혜택(리마인드, 학습 코칭)으로 설계한다.
- 잘못 부른 위험군의 피해가 크면 정밀도를 우선하고, 점수만으로 수강 제한이나 불이익을 주지 않는다.

가상 데이터 500건의 점수는 **모델 실습 결과**다. 실제 교육 서비스의 예측 성능으로 보고서 문장에 쓰지 않는다. 성능이 낮으면 숫자 그대로 두고, 데이터와 검증이 더 필요하다는 결론으로 잇는다.

재현하려면 난수 시드를 고정한다. 시드가 없으면 같은 코드를 다시 실행할 때 데이터가 바뀌어 회의에서 숫자가 달라진다.

## 10. Gemini와 파이썬을 연결할 때

파이썬은 숫자를 계산하고, Gemini는 그 숫자를 문장으로 푼다. 역할을 바꾸면 보고서가 흔들린다.

```text
파이썬: 가입자 수, 전환율, 수료율, 만족도, 모델 점수를 계산해 JSON으로 정리
Gemini: 그 JSON만 근거로 요약, 문제, 제안, 추가 확인을 작성
사람: 사실 / 가설 / 아직 모르는 것을 구분해 채택
```

API를 붙일 때 기획 문서에 들어갈 항목

- **키 관리**: API 키는 코드, 노트북, 채팅, 캡처에 적지 않는다. Colab의 비밀정보 기능처럼 실행 환경의 비밀 저장소를 쓴다.
- **실패 경로**: 키가 없거나 호출이 실패하면, 파이썬이 계산한 표만이라도 출력되게 한다.
- **모델 이름**: 사용 가능한 모델명을 확인한 뒤 설정한다. 기억 속의 모델명으로 고정하지 않는다.
- **비용**: 호출 횟수, 입력 길이, 재시도가 비용을 만든다. 원본 고객 로그 전체를 프롬프트에 넣지 않고 집계값만 넣는다.
- **개인정보**: 이름, 연락처, 자유 서술 상담 내용, 식별 가능한 학습 로그는 외부 모델에 보내기 전에 제거하거나 승인 절차를 둔다.
- **과장 금지**: 규칙으로 질문을 분류한 프로토타입을 생성형 에이전트라고 쓰지 않는다. 기능 표에 구현 수준과 한계를 적는다.

보고서 문장은 다섯 칸이면 충분하다.

1. 분석 요약
2. 주요 지표
3. 발견된 문제
4. 개선 제안
5. 추가 확인이 필요한 사항

1~3은 계산된 사실에 붙이고, 4는 제안으로, 5는 데이터에 없는 원인으로 둔다.

## 11. AI에게 파이썬을 시키는 요구사항 쓰는 법

좋은 지시문은 기능 설명이 아니라 **입력, 규칙, 출력, 금지**가 분리된 짧은 기획서다.

### 11.1 지시문 골격

```text
나는 프로그래밍 비전공자인 AI 서비스 기획자이다.
Google Colab Enterprise에서 실행할 파이썬을 만들어 달라.

[업무 목표]
한 문장.

[데이터]
항목 이름, 행의 단위, 건수, 가상 데이터인지.

[규칙]
계산식, 기준값, 예외(결측, 범위 밖, 중복) 처리.

[출력]
표로 볼 열, 그래프 종류, 마지막에 필요한 문장.

[제약]
한글 주석, 설치 금지 여부, API 키를 코드에 넣지 말 것,
실행 결과와 해석을 구분할 것.

[완료 후]
구현한 기능, 실제 서비스에 더 필요한 기능,
기획자가 직접 검토할 사항을 정리할 것.
```

### 11.2 모호한 문장과 실행 가능한 문장

| 모호해서 결과가 흔들리는 말 | 실행 가능한 말 |
| --- | --- |
| 매출을 분석해 줘 | 수량 × 단가로 매출액을 구하고, 전체 대비 비중과 최댓값 상품을 표로 출력 |
| 나쁜 데이터를 지워 줘 | 결측, 중복 ID, 음수 금액, 만족도 범위 밖, 날짜 형식 오류를 유형별로 세고, 삭제·보정·검토로 나눠 처리. 원본은 유지 |
| 예쁜 대시보드 | 월별 가입자는 선 그래프, 유료 전환 수는 막대그래프. 축과 제목은 한글 |
| 이탈을 AI로 예측 | 가상 500건, 로지스틱 회귀, 학습/테스트 분리, 정확도·정밀도·재현율·F1·혼동 행렬 |
| 보고서를 잘 써 줘 | 계산된 JSON만 근거로 쓰고, 사실·가설·추가 확인을 구분해 5개 목차로 작성 |

### 11.3 결과를 받은 뒤 기획자가 하는 검토

- 요구한 컬럼이 모두 있는가
- 기준값(4점 미만, 상위 20%)이 코드와 출력에 같은가
- 합계, 비중, 평균이 서로 모순되지 않는가. 비중 합은 100% 근처인가
- 가상 데이터라고 적혀 있는가
- 인사이트 문장이 표에 있는 숫자를 가리키는가
- 개인정보, API 키, 비밀번호가 셀에 없는가
- Colab에서 되는 일과 별도 서버·웹 앱이 필요한 일이 구분되어 있는가

## 12. 실습 8개와 언어 개념 지도

| 실습 | 기획 과제 | 이때 읽는 파이썬 |
| --- | --- | --- |
| 1. 파이썬 기초 | 쇼핑몰 월간 매출 | 변수, 사칙연산, 리스트, 반복, 표 출력 |
| 2. 요구사항으로 코드 생성 | 과정별 만족도 | 조건, 기준값, 범위 검증, 단계 분리 |
| 3. NumPy·Pandas | 고객 100명의 구매 | DataFrame, 평균·중앙값, 그룹 비교 |
| 4. 데이터 클렌징 | 오류가 섞인 고객 표 | 결측, 중복, 형식 변환, 원본 보존 |
| 5. 시각화 | 교육 플랫폼 운영 현황 | 그래프 종류, 축, 패턴과 가설의 구분 |
| 6. 질문형 프로토타입 | 자연어로 지표 조회 | 규칙 기반 분기, 근거 출력, 구현 수준 표 |
| 7. 기초 예측 | 중도 이탈 위험 | 입력과 정답, 성능 지표, 시드, 누수 |
| 8. Gemini API | 분석 보고서 생성 | JSON, 비밀정보, 실패 시 대체 출력 |

실습이 진행될수록 문법이 늘어나는 것이 아니라, **같은 표 처리 위에 품질 규칙, 그림, 예측, 문장 생성**이 하나씩 붙는다.

## 13. 서비스에 올릴 때 기획서가 가져야 할 파이썬 관점 항목

프로토타입을 기능 요구서로 올릴 때는 코드 첨부보다 아래 표가 먼저다.

| 항목 | 적을 내용 |
| --- | --- |
| 사용자와 사용 시점 | 운영자가 주간 회의 전에 보는가, 수강생에게 실시간으로 보이는가 |
| 입력 데이터 | 항목, 출처, 갱신 주기, 개인정보 여부 |
| 집계 단위 | 사람, 주문, 과정, 월 |
| 지표 정의 | 분자, 분모, 기간, 반올림 |
| 예외 규칙 | 결측, 중복, 범위 밖, 0으로 나누기 |
| 출력 | 화면의 표, 그래프, 알림, 다운로드 |
| 사람 승인 | 자동 반영과 검토 후 반영의 경계 |
| 모델이 있을 때 | 학습 데이터 기간, 성능 기준, 불이익 금지 원칙 |
| 생성형이 있을 때 | 전달하는 데이터 범위, 키 관리, 비용 상한, 실패 시 화면 |
| 아직 Colab에만 있는 것 | 로그인, 권한, 저장, 스케줄, 감사 로그는 별도 개발 범위 |

0으로 나누기는 기획 지표에서 자주 나온다. 신청자가 0인 과정의 수료율은 계산하지 않고 “산출 불가”로 둔다.

## 15. 한 장 요약

1. 파이썬은 이 과정에서 **기획 규칙을 실행해 표와 그래프로 확인하는 도구**다.
2. 직접 작성보다, 입력·규칙·출력·예외를 문장으로 고정한 뒤 AI에게 코드를 맡긴다.
3. 변수, 조건, 반복, 함수, DataFrame만 읽을 수 있어도 실습 코드의 대부분은 따라간다.
4. 숫자는 코드 실행 결과만 쓰고, 해석과 가설은 그 옆에 분리해 적는다.
5. 가상 데이터, 낮은 모델 점수, 계산 불가 항목은 숨기지 않는다.
6. API 키와 개인정보는 코드와 프롬프트에 넣지 않는다.
7. Colab에서 확인한 프로토타입과, 권한·저장·운영이 필요한 실제 서비스 범위를 문서에서 나눈다.

다음 실습을 시작할 때는 공통 지시문을 먼저 붙인다. 전문은 `AI 주도형 파이썬 스크립트 실무 실습 프롬프트.txt` 마지막의 「공통으로 사용할 수 있는 프롬프트」를 그대로 사용한다.
